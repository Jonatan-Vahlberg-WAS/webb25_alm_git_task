### Dependency notation

Some issues list dependencies so the team can sequence work and PRs:

- **Blocked by:** another issue (or **none**) — you cannot reasonably finish *all* acceptance criteria until the blocker is merged or otherwise satisfied.
- **Partially blocked by:** another issue or external dependency — part of the work can start early (mocks, layout, types), but integration, end-to-end behaviour, or sign-off waits on that dependency.

If a line is omitted, treat it as **none** for that category.

### Issue 16 - Implement category handling in the frontend

**Type:** `enhancement`

**Blocked by:** none (among Issues 16–19).

**Partially blocked by:** backend delivery of `/categories` CRUD and a clear contract for how `Product` references `Category` (from your Category backend work, which may be tracked outside this file). You can still add client modules and UI shells early, but replacing the product category dropdown and showing populated categories on products is partially blocked until that API and payload shape exist.

The app currently hardcodes product categories in `frontend/src/App.jsx`. Once the API exposes `/categories` (and products reference categories as agreed with the backend), the client should drive category data from the API instead of static enums.

**Tasks**

- Add a `frontend/src/api/categories.js` module that calls `GET`, `GET/:id`, `POST`, `PUT/:id`, and `DELETE` on `/categories`, reusing the same error-handling style as `frontend/src/api/products.js`.
- Add UI for full category CRUD (list with `name`, `description`, `isActive`; create and edit forms; delete with confirmation; loading and error states consistent with the products UI).
- Replace the hardcoded `CATEGORIES` select for products with options loaded from the API (active categories only, or all categories if the API does not filter—document the choice).
- Show each product’s category in the list when the API returns a reference or populated category.
- Update `frontend/.env.example` if any new env vars are required; keep `npm run lint` and `npm run build` passing in `frontend/`.

**Acceptance criteria**

- Categories are created, listed, updated, and deleted entirely through the UI against the real API (no hardcoded category lists for CRUD or for the product category dropdown).
- Product create/update sends the shape the backend expects (`category` id or agreed field).
- Invalid or empty API responses are handled without silent failures.

### Issue 17 - Add User model and authentication middleware on the backend

**Type:** `enhancement`

**Blocked by:** none.

**Partially blocked by:** none.

Introduce a persisted `User` model and server-side authentication so protected routes can be gated before the frontend work in Issue 18.

**Tasks**

- Define a Mongoose `User` schema with at least `email`, `password` (stored hashed only), and any fields you need for your auth strategy (e.g. `name`).
- Enforce `email` as unique at the schema or application level with clear errors on duplicate registration.
- Hash passwords on create (and when the password is intentionally changed—see Issue 19 for update semantics).
- Implement registration and login (or equivalent) endpoints that issue your chosen credential (e.g. JWT in response or http-only cookie—pick one approach and document it).
- Add authentication middleware that verifies the credential and attaches the user (or user id) to `req` for downstream handlers.
- Apply the middleware to routes that should require a logged-in user (e.g. selected product or category mutations, or a dedicated `/me` route).

**Acceptance criteria**

- Unauthenticated requests to protected routes receive `401` (or your documented status), not `500` from missing auth.
- Passwords never appear in API responses or logs.
- Duplicate `email` registration fails with a predictable client-facing error.

### Issue 18 - Implement authentication handling in the frontend

**Type:** `enhancement`

**Blocked by:** Issue 17 — you need stable registration/login (or equivalent), the chosen credential format, CORS/cookie behaviour, and at least one protected route to integrate against.

**Partially blocked by:** none (optional spike: static login/register screens with mocked responses, but do not treat Issue 18 as done until Issue 17 is in place).

Wire the React app to the auth API from Issue 17 so users can sign in and use protected features from the browser.

**Tasks**

- Add screens or flows for register and login (and logout) consistent with the backend contract.
- Persist the session safely for your mechanism (e.g. store JWT in `memory` + `sessionStorage` tradeoffs, or rely on http-only cookies with `credentials: 'include'`—match the backend CORS and cookie settings).
- Attach the auth header or credentials on requests to protected endpoints (centralize in the API layer, not scattered `fetch` calls).
- Gate UI: hide or disable actions that require auth when logged out; show errors from `401`/`403` clearly.
- Extend `frontend/.env.example` if needed (e.g. no secrets; only public base URLs already documented).

**Acceptance criteria**

- A user can register, log in, call at least one protected operation, log out, and lose access to that operation until logging in again.
- No plaintext passwords stored in `localStorage` unless the course explicitly allows it—prefer patterns aligned with Issue 17.

### Issue 19 - Add tests for the User model (email, password hashing, selective re-hash)

**Type:** `test`

**Blocked by:** Issue 17 — tests for hashing, login, and “update name without re-hashing password” require the real `User` schema and the update path you ship in Issue 17.

**Partially blocked by:** none (if the team agrees on field names early, you may sketch `describe` blocks and fixtures, but keep **Blocked by** in mind before merging tests that assert behaviour not yet implemented).

Cover user persistence and update behavior so regressions around security and uniqueness are caught early.

**Tasks**

- Test that `email` must be unique: creating two users with the same email fails (assert on validation or duplicate key error, depending on implementation).
- Test that stored `password` is never plain text: after create, the value in MongoDB (or the loaded document’s `password` field) is a hash different from the raw password; login still succeeds with the raw password.
- Test that updating a user’s non-password fields (e.g. `name`) does **not** change the stored password hash when the password is omitted from the update payload.
- Test that updating **only** the password produces a new hash and that login works with the new password and fails with the old one.

**Acceptance criteria**

- All of the behaviors above are asserted explicitly in tests (not only implied by manual checks).
- Tests remain stable (no reliance on wall-clock timing except where unavoidable for tokens, if applicable).
